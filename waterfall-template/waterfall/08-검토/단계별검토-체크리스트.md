## 단계별 검토

문서의 존재와 기록은 확인했다. G0~G6은 각 단계의 검토 및 승인 증빙이 확보됐을 때 판단한다. 아래 체크박스는 단계 전환에 필요한 항목이며, 실제 완료 증거가 들어오면 갱신한다.

## Phase 0 기획 검토

근거는 [서비스기획서](../00-기획/서비스기획서.md)와 [비즈니스정책서](../00-기획/비즈니스정책서.md)다.

- [ ] Android MVP의 포함·제외 범위, 테스트 코인 거래, 시범 검증 기준을 검토한다.
- [ ] 레어도별 동봉, 매입가와 팩, 배송·계정 미결 정책을 확인하고 영향 범위와 결정 일정을 기록한다.

## Phase 1 요구사항 검토

근거는 [SRS](../01-요구사항분석/요구사항명세서-SRS.md), [유스케이스](../01-요구사항분석/유스케이스명세서.md), [RTM](../01-요구사항분석/요구사항추적매트릭스-RTM.md)이다.

- [ ] 적용 범위의 요구사항에 출처, 수용 기준, 정상 및 예외 흐름이 연결되어 있다.
- [ ] 미결 정책값과 운영 범위가 관련 요구사항 및 테스트에 표시되어 있다.

## Phase 2 시스템 설계 검토

근거는 [SAD](../02-시스템설계/시스템아키텍처설계서-SAD.md), [API](../02-시스템설계/API설계서.md), [DB](../02-시스템설계/데이터베이스설계서.md), [화면설계서](../02-시스템설계/화면설계서.md)다.

- [ ] 권한, 레어도 코드별 배정, 요청 재전송 및 실물·코인 기록의 일관성을 확인한다.
- [ ] 운영자 화면과 인증, 서버·저장소 환경 및 접근성 계획을 검토한다.

## Phase 3 상세 설계 검토

근거는 [상세설계서](../03-상세설계/상세설계서.md)다.

- [ ] 확정·실패·재시도 처리와 배송·재매입 경합, 반려 카드 제외의 구현 단위를 검토한다.
- [ ] 개발 도구와 데이터 환경, 미결 운영 정책이 구현에 미치는 영향을 확인한다.

## Phase 4 구현 검토

### 4.5 G4 테스트 인계

근거는 [구현·테스트 인계서](../04-구현/구현-테스트-인계서.md)다.

- [ ] 구현 커밋, APK·서버 빌드와 실행 방법, 환경 및 인수자를 연결한다.
- [ ] 구현 점검·코드 리뷰 증빙과 변경 사항을 RTM에 연결한다.
- [ ] QA 계정과 데이터, [테스트계획서](../05-테스트/테스트계획서.md)의 진입 조건을 확인한다.

## Phase 5 테스트 검토

근거는 [테스트케이스](../05-테스트/테스트케이스.md)와 [테스트결과보고서](../05-테스트/테스트결과보고서.md)다.

- [ ] 해당 후보 빌드의 정상·예외·동시 요청·접근성 검증 결과를 확인한다.
- [ ] 출시 차단 결함의 수정·재검증 또는 남은 제약의 승인 근거를 기록한다.
- [ ] 종료 기준 충족 여부와 배포 판단을 기록한다.

## Phase 6 배포 검토

### 6.5 G6 운영 인수

근거는 [배포계획서의 G6 기록](../06-배포/배포계획서.md#35-g6-운영-인수-기록)과 [운영가이드](../06-배포/운영가이드.md)다.

- [ ] 실제 버전·환경과 배포 후 점검 증빙을 기록한다.
- [ ] 운영 인수자가 알림·모니터링, 장애 대응과 복구 절차에 접근할 수 있다.
- [ ] 남은 이슈·담당자·기한과 인수자·일시를 [유지보수계획서](../07-유지보수/유지보수계획서.md)에 연결한다.
